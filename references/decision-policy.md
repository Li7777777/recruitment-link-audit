# 减少过度待核实：名称直判、独立维度与复核分流

## 1. 原因与修正目标

旧流程存在几类会放大“待审核”的问题：

- 把“应优先看真实职责”理解成“没有完整JD就不能判断任何岗位”。
- 非技术岗位没有展示专业要求时，因担心其可能符合T3而全部悬置；但T3本来需要明确的正面专业证据。
- 已有可靠官方校招上下文，却要求每个岗位再次逐字写出“校招正式岗位”。
- 把个人资料未提供、城市缺失、限投未知等和岗位方向混在一个待核实状态里。
- 旧导出器对所有 eligibility=待核实/未评估 的岗位自动逐行生成“需复核”，包括明确不纳入或已排除的岗位；多城市又重复放大。
- 城市曾作为岗位子等级，排除/不纳入后不允许保存城市等级，导致已知地点也丢失。

修正不是把所有未知变成确定，而是**先判断已能判断的维度，剩余真实阻断单列**。不得为了好看的待核实率猜测招聘开放、限投数、个人资格或来源范围。

## 2. 证据梯度

1. **明确职责/专业/招聘类型反证**：足以推翻仅凭名称的判断，以具体事实为准。
2. **明确岗位名称**：当名称已能识别方向且无反证时，直接归类并引用名称，不强制要求完整JD。
3. **官方分类/部门/本轮招聘上下文**：用于解释宽泛标题和招聘类型；上下文必须确实覆盖该岗位。
4. **仍不明确的关键方向**：有限补查岗位详情、公告/岗位表或同一岗位的其他官方来源；不要因每个无关字段缺失而无限追查。

记录 classification_basis=岗位名称/岗位职责/招聘专业/综合，classification_confidence=高/中/低。置信度是证据强弱说明，不自动变成需人工审核；仅名称直判通常为中，有职责印证可为高，不应伪装已读JD。

## 3. 名称直判示例与边界

下列等级只适用于用户选择的规则确实定义相应方向时，不能替代其他用户的规则。

| 岗位名称或已有证据 | 可做的判断 | 不必等待的信息 |
| --- | --- | --- |
| Agent开发、RAG应用、大模型应用开发 | 岗位T0 | 不要求先补专业/学历/完整JD |
| NLP算法、LLM算法 | 岗位T1 | 不因未知个人资格而丢掉方向 |
| Java开发、后端、前端、测试开发、数据开发 | 岗位T2 | 专业栏缺失不影响明确技术方向 |
| 明确计算机算法研发，但未确认应用/NLP细分 | 当前证据T2 | 不为追求T0/T1而全项待核实 |
| 图像分割、计算机视觉、模型推理优化、嵌入式、FPGA | 规则排除 | 无反证时名称已能命中黑名单 |
| 柜员、客户经理、诉讼合规、行政等明确非计算机技术岗，未见计算机类专业 | 按当前证据不纳入 | 不推测“也许专业接受计算机”而悬置 |
| 同上非技术岗，但明确接受计算机类专业 | 可为T3 | 不能仅凭非技术名称不纳入 |
| 系统管理、科技支持、研发岗、技术员，所属类别/职责也不清楚 | 关键方向待核实 | 不把“系统/研发/科技”当自动纳入关键词 |

不要用机械子串替代语义：AI产品经理不因“AI”升T0；普通Web部署不因“部署”命中模型Infra；硬件公司的后端不因行业排除；销售标题出现客户“系统”不等于软件研发。

“未见计算机专业依据”只表示当前证据未达到T3要求，不能写成“明确不招计算机专业”。后续补充正面专业证据后重新判断。

## 4. 独立维度及阻断条件

- **direction_result / priority**：方向是否匹配和岗位等级，由名称/职责/专业判断。
- **result**：本次最终筛选，受用户要求的招聘类型等门槛影响，不等于个人资格结论。
- **status**：具体岗位是否仍在招，必须另有开放/关闭证据，不从名称推断。
- **city_priority**：仅看实际工作地区，和岗位等级、最终排除/待核实无依赖。
- **eligibility**：个人是否符合已知招聘条件，不把未知填成符合，也不连带推翻明确方向。
- **quota**：官方限投规则，未知不猜，不让未知限额把岗位方向改成待核实。

只有 direction_result=纳入 而 result=待核实时，保留 priority，并在 blocking_issues 明确真正门槛，例如“方向已确认Agent开发，但是否正式校招尚不明确”。这类岗位不进入匹配在招候选计数，排序也不能冒充最终纳入。

方向确实无法分类时，direction_result=待核实，priority留空；有已知实际城市时 city_priority照常填写。排除/不纳入/停招同样保留城市等级。

## 5. 哪些应标“需复核”

**阻断复核**：真实影响最终筛选的歧义或冲突、无法确认当前候选是否仍开放、类型门槛不明确，以及显式填写的blocking_issues。必须解释“缺什么、会改变哪项结论”。

**非阻断补充**：个人学历/届次资料未提供、仅缺城市、清晰名称直判但无完整JD、未确认更高岗位等级、其他不影响当前结论的详情缺项。放nonblocking_notes或对应字段，不一律标需复核。

原uncertainties继续在岗位表完整展示，**不再因为该字段非空就自动标红复核**；不要把真实阻断藏到nonblocking_notes，也不要靠分类标签掩盖访问失败。

个人资格提示按单位对仍有意义的匹配在招候选去重汇总，不逐城市重复生成，也不对已排除/不纳入岗位反复要求提供个人资料。岗位阻断事项按真实投递身份和具体问题去重，不把同岗多城市当多个同样问题。

不设置“待核实率必须低于某值”的指标，不自动按名称重写历史报告。若用户要求重跑，使用新规则和对应证据重新生成，保留旧报告/旧规则快照，不能更新旧时间冒充重新核验。

## 6. 本次独立城市规则

当用户选择随附岗位规则时：城市T0=江浙沪；城市T3=新疆、西藏、内蒙古、山西、北京、青海及所属城市；其他明确地区T1；地点未知单列待核实。本版没有城市T2。

该规则属于用户指定文件而非导出器内置常量。导出器接收run.city_priority_order=["T0","T1","T3"]及每行独立city_priority，支持所有筛选结果保留该列。旧JSON空城市等级可兼容读取，但显示为尚未评级的补充提示；新任务必须对每行独立评级，不得复制岗位等级。
